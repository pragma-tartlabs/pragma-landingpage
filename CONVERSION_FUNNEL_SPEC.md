# Pragma Phase 1 Conversion Funnel Specification
**Complete acquisition flow: landing page → waitlist → onboarding → Foundation Stack**

---

## Overview

The conversion funnel recruits the first 1,000 women into the Pragma founding cohort. The funnel captures email, generates a unique position in queue, enables referral tracking, and sequences the user through onboarding.

### Funnel Stages

```
Landing Page → Email Submission → Confirmation Page → Welcome Email → Nurture Sequence → Onboarding App → Intake Flow → Foundation Stack
```

### Key Metrics

| Metric | Target | Owner |
|---|---|---|
| Landing page → email submission | ≥ 10% conversion | Product |
| Email submission → confirmation page view | 100% (transactional) | Product |
| Welcome email open rate | ≥ 40% | Marketing |
| Onboarding flow start (when app ready) | ≥ 70% | Product |
| Intake module 1 completion | ≥ 80% | Product |
| Protocol completion (after 2 modules) | ≥ 70% | Product |
| Referral conversion (referee → signup) | ≥ 15% | Product/Marketing |

---

## 1. Post-Submission Flow

### Step 1.1: Email Submission
**Trigger:** User clicks "Join the founding cohort" button on landing page

**Form validation:**
- Email format: valid email address (RFC 5322)
- Duplicate check: if email already exists in waitlist, show message "You're already on the list! Check your email for your referral link."
- Rate limiting: max 1 signup per IP per 5 seconds (prevent spam)

**On submit:**
1. Email is collected
2. System generates unique `referral_code` (8-char alphanumeric, e.g., `WB7K2M9X`)
3. Current queue position is calculated (count existing signups + 1)
4. Signup record created in Supabase `waitlist` table
5. ConvertKit subscriber created/updated with email + tags
6. User is redirected to confirmation page (URL: `/confirm?email=user@email.com&position=42`)
7. Transactional email queued (welcome email via ConvertKit)

---

### Step 1.2: Confirmation Page
**URL:** `/confirm?email=[email]&position=[position]`

**Display:**
- Email address (obfuscated option: "j***@email.com" or full)
- Position in queue: "You're #42 of 1,000"
- Referral section (see section 1.3)
- Countdown to 1,000 slots filled (if desired)
- CTA: "Copy my referral link" + social share buttons

**Behavior:**
- Page loads data from Supabase to fetch position (or pass position as URL param for instant display)
- If position > 1,000, show message: "Waitlist is full. Join the email list for updates." (fallback to standby list)
- Session cookie: store email to remember user (for later referral tracking)

---

### Step 1.3: Referral System
**Trigger:** User arrives at confirmation page

**Design:**
- Each user gets a unique referral code + shareable link
- Link format: `pragma.health/join?ref=[referral_code]` or `pragma.health/?ref=[referral_code]`
- Referral page: lands on landing page with `?ref=` parameter pre-filled (system tracks source)

**Mechanics:**
- Referrer must have valid email in waitlist
- Referee (clicked link) can be new or existing signup
- If new signup via referral: record in `referrals` table as `status: pending`
- If referee converts (completes signup): `referrals.status: converted`
- Position boost: For every 3 converted referrals, referrer moves up 50 spots (max 150 spots)

**Validation:**
- Duplicate referral: if same referee already credited to this referrer, ignore
- Invalid code: redirect to landing page (no error shown, avoid leaking user list)

## 2. Data Collection at Signup

### Collected at submission:
- `email` — primary identifier
- `created_at` — timestamp (UTC)
- `ip_address` — for rate limiting + analytics
- `utm_source` — traffic source (organic, social, email, referral, etc.)
- `utm_medium` — medium (social, email, cpc, organic, referral)
- `utm_campaign` — campaign identifier
- `referral_code` — (generated by system, not user input)
- `position` — calculated at signup time
- `status` — enum: `pending` (in queue), `converted` (completed intake), `churned` (unsubscribed), `standby` (if >1,000)

### Not collected at signup:
- Name
- Age
- Health data
- Preferences

**Why:** Keep signup friction minimal. Health data collected in intake flow (phase 2 of funnel).

### Analytics captured:
- Event: `signup_email_submitted` (Supabase function or client-side analytics)
- Event properties:
  - `email_domain` (gmail, yahoo, corporate, etc.)
  - `timestamp`
  - `utm_source`, `utm_medium`, `utm_campaign`
  - `referral_code_used` (if applicable)
  - `position`

## 3. Supabase Schema for Phase 1

### Table: `waitlist`
Purpose: Track all signups, positions, and referral codes

```sql
CREATE TABLE waitlist (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email VARCHAR(255) NOT NULL UNIQUE,
  referral_code CHAR(8) NOT NULL UNIQUE,
  position INTEGER NOT NULL, -- calculated at signup
  referral_count INTEGER DEFAULT 0, -- count of converted referrals
  position_boost INTEGER DEFAULT 0, -- cumulative boost from referrals (0, 50, 100, 150)
  utm_source VARCHAR(100),
  utm_medium VARCHAR(100),
  utm_campaign VARCHAR(100),
  ip_address INET,
  status VARCHAR(50) NOT NULL DEFAULT 'pending', 
    -- enum: pending, converted, churned, standby
  convertkit_subscriber_id INTEGER, -- ConvertKit ID for sync
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  last_email_clicked_at TIMESTAMP WITH TIME ZONE,
  notes TEXT
);

CREATE INDEX idx_waitlist_email ON waitlist(email);
CREATE INDEX idx_waitlist_referral_code ON waitlist(referral_code);
CREATE INDEX idx_waitlist_position ON waitlist(position);
CREATE INDEX idx_waitlist_status ON waitlist(status);
CREATE INDEX idx_waitlist_created_at ON waitlist(created_at);
```

### Table: `referrals`
Purpose: Track referral relationships (referrer → referee → conversion)

```sql
CREATE TABLE referrals (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  referrer_id UUID NOT NULL REFERENCES waitlist(id) ON DELETE CASCADE,
  referrer_email VARCHAR(255), -- denormalized for queries
  referee_email VARCHAR(255) NOT NULL,
  referral_code CHAR(8) NOT NULL, -- code used by referee
  status VARCHAR(50) NOT NULL DEFAULT 'pending',
    -- enum: pending (clicked link), converted (completed signup), credited (position boost applied)
  referee_waitlist_id UUID REFERENCES waitlist(id) ON DELETE SET NULL, -- once referee signs up
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  converted_at TIMESTAMP WITH TIME ZONE,
  credited_at TIMESTAMP WITH TIME ZONE
);

CREATE INDEX idx_referrals_referrer_id ON referrals(referrer_id);
CREATE INDEX idx_referrals_referee_email ON referrals(referee_email);
CREATE INDEX idx_referrals_status ON referrals(status);
CREATE INDEX idx_referrals_referral_code ON referrals(referral_code);
```

### Table: `analytics_events`
Purpose: Track user actions (email opens, link clicks, page views, etc.)

```sql
CREATE TABLE analytics_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  waitlist_id UUID REFERENCES waitlist(id) ON DELETE CASCADE,
  email VARCHAR(255), -- denormalized if waitlist_id is null
  event_type VARCHAR(100) NOT NULL,
    -- examples: signup, confirmation_page_view, referral_link_clicked, 
    --           welcome_email_opened, intake_started, protocol_received, conversion_started
  event_properties JSONB, -- flexible key-value store
  timestamp TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_analytics_events_waitlist_id ON analytics_events(waitlist_id);
CREATE INDEX idx_analytics_events_event_type ON analytics_events(event_type);
CREATE INDEX idx_analytics_events_timestamp ON analytics_events(timestamp);
```

### Table: `waitlist_position_history` (optional, for auditing)
Purpose: Track position changes over time (for transparency/debugging)

```sql
CREATE TABLE waitlist_position_history (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  waitlist_id UUID NOT NULL REFERENCES waitlist(id) ON DELETE CASCADE,
  old_position INTEGER,
  new_position INTEGER,
  reason VARCHAR(100), -- 'new_signup', 'referral_boost', 'churn_reorder'
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_position_history_waitlist_id ON waitlist_position_history(waitlist_id);
```

### Functions/Triggers

**Function: `calculate_position_on_signup()`**
- Called when new waitlist record is inserted
- Returns: count of existing non-churned signups + 1
- Updates: `waitlist.position`

**Function: `apply_referral_boost()`**
- Called when referral status changes to `credited`
- Fetches referrer, counts converted referrals
- If count % 3 == 0: applies 50-spot boost to referrer's position
- Updates: `waitlist.position_boost`, `waitlist.position`
- Cascades: recalculates all downstream positions (O(n), run offline if >1,000)

**Trigger: `update_waitlist_updated_at`**
- Fires on any UPDATE to `waitlist` table
- Sets `updated_at = now()`

## 5. Referral System Design

### Overview

**Goal:** Grow waitlist virally by incentivizing early adopters to refer friends.

**Mechanics:**
- Each user gets unique referral code
- Sharing code is optional (no gate, no friction)
- For every 3 friends who convert (complete signup), referrer moves up 50 spots
- Max boost: 150 spots (9 referrals)
- Boost applies immediately (not retroactive)

---

### Referral Link

**Format:** `https://pragma.health/join?ref=[referral_code]`

**Alternative:** Short link via Bit.ly or custom shortener
- Shorter: `https://pragmahealth.co/join/ABC123XYZ`
- Benefit: easier to share on social, trackable

**Behavior when clicked:**
1. Landing page loads with `?ref=` parameter
2. System checks if `referral_code` is valid
3. If valid: store in session/localStorage (user hasn't signed up yet)
4. If invalid: ignore, show landing page normally
5. User submits email
6. On signup: system checks for stored `ref` param, creates record in `referrals` table with `referee_email` and `referral_code`

---

### Conversion Logic

**Referee signs up:**
1. Email submitted with `?ref=ABC123XYZ` in URL
2. Create `waitlist` record with email + generate new referral_code
3. Create `referrals` record:
   - `referrer_id` = waitlist record matching `ABC123XYZ`
   - `referee_email` = newly signed up email
   - `status = pending`
4. Send "You were referred by someone! Consider sharing too" email (optional)

**Referral converted:**
- Manual trigger (admin marks as converted) OR system auto-marks after 7 days (referee is actively using app)
- Update `referrals.status = converted`
- Increment `waitlist.referral_count` for referrer
- Check if `referral_count % 3 == 0`:
  - If yes: apply 50-spot boost (`position_boost += 50`, `position -= 50`)
  - If no: do nothing
- Tag referrer in ConvertKit: `pragma-referrer` or `pragma-referrer-x3` (for email segmentation)

---

### Position Boost Calculation

**Formula:**
```
position_boost = floor(referral_count / 3) * 50
adjusted_position = base_position - position_boost
```

**Example:**
- User signs up at position 150 (150 people ahead)
- Refers 3 friends → 1 boost tier → position becomes 150 - 50 = 100
- Refers 6 friends total → 2 boost tiers → position becomes 150 - 100 = 50
- Refers 9 friends total → 3 boost tiers (max) → position becomes 150 - 150 = 1 (or tied with others at position 1)

**Edge case: Boost would put position < 1**
- Cap at position = 1
- Display: "You're at the top of the waitlist!"

---

### Referral Tracking Dashboard (optional, in-app)

**Display:**

---

### Fraud Prevention

**Checks:**
- No self-referral: if `referee_email == referrer_email`, ignore
- No duplicate referral: if same email already referred by this person, ignore (count only first)
- Rate limit: same IP can refer max 10 emails in 24 hours
- Domain validation: no spam domains (guerrillamail, tempmail, etc.) — flag for manual review
- Conversion validation: referee must complete at least 1 intake module (or open app) to count as converted

## 6. Waitlist Position Logic

### Initial Position Calculation

**On signup:**
```
position = COUNT(SELECT id FROM waitlist WHERE status != 'churned' AND created_at < NOW()) + 1
```

**Stored in:** `waitlist.position`

**Display to user:** Position shown immediately on confirmation page

---

### Position Drift & Reordering

**Scenario 1: Someone ahead churns**
- User at position 50, 20 people ahead churn
- User's position automatically drops to 30? OR stays at 50?

**Recommendation:** Position is immutable (doesn't drift). It's "spot in queue when you signed up," not "people ahead of you right now."

**Rationale:**
- Simpler to track
- No surprises when user returns to check position
- Easier to communicate ("You're spot #42")

---

### Position Boost from Referrals

**When applied:**
- Immediately upon conversion (within 24 hours of referee signup)
- Recalculated whenever referral count changes

**How it affects position:**
```
adjusted_position = position - position_boost
```

**Edge cases:**
- Referral boost is capped at 150 (3 boost tiers max)
- If adjusted position < 1, cap at 1
- If multiple users have same adjusted position, sort by `created_at` (earlier wins)

---

### Position Reordering (Churn handling)

**Current approach:** Don't reorder (positions are static).

**Alternative approach:** Reorder daily to keep positions 1–1,000 compact.
- Pros: no gaps, fairer ordering
- Cons: positions change daily (confusing UX)
- Cost: O(n) recalculation

**Recommendation:** Don't reorder. Keep it simple. Use a `standby` status for >1,000.

---

### Position Display Rules

**Rule 1:** Show actual position to user (not estimate)
- "You're #42 of 1,000"

**Rule 2:** Show countdown (if desired)
- "200 spots left!" (based on how many pending vs. standby)

**Rule 3:** Show boost benefit
- "Refer 3 more friends to move up 50 spots"

**Rule 4:** If position ≥ 1,000
- Status = `standby` (or `waitlist_full`)
- Message: "We're at capacity for Phase 1. You're on the standby list. We'll notify you if spots open."

## Appendix: Supabase Security & Permissions

### Row-Level Security (RLS)

**`waitlist` table:**
- Public read: Anyone can read positions (for transparency)
- Public insert: Allowed (anyone can sign up)
- Update/delete: Only authenticated admin or user's own record (for updates like unsubscribe)

**`referrals` table:**
- Public read: Only own referrals (not others')
- Public insert: Allowed (system creates on signup)
- Update/delete: Only admin

**`analytics_events` table:**
- Public insert: Allowed (client-side tracking)
- Public read: None (sensitive data)
- Read: Only admin

### Data Privacy

- No PHI (personally identifiable health data) stored in Phase 1
- Email is the PII, encrypted at rest
- No passwords stored (passwordless auth if app requires it later)
- GDPR-compliant: deletion endpoint ready for Phase 2
- HIPAA-ready: infrastructure supports HIPAA compliance for Phase 2 when health data collected
